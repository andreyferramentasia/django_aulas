Agora que existem contas, dá para proteger as views do CRUD. São dois mixins, cada um responde uma pergunta:

LoginRequiredMixin
Está logado? Qualquer usuário logado entra, não importa quem seja. Quem não está logado vai para a tela de login.
PermissionRequiredMixin
Pode fazer isso? Além de logado, o usuário precisa ter a permissão indicada. Logado sem permissão recebe erro 403 (proibido).

? Quando usar cada um

SituaçãoUseExemplo
Todo usuário logado pode ver ou fazerLoginRequiredMixinVer a lista de pessoas. Se for o único mixin do CRUD, qualquer usuário logado também cadastra, edita e exclui.
Só alguns usuários podem fazerPermissionRequiredMixinCadastrar, editar, excluir
Qualquer um, mesmo sem contaNenhumLogin e cadastro de conta

1 Dizer onde fica o login

No fim do settings.py. Assim não precisa repetir o login_url em cada view:

LOGIN_URL = "accounts:login"

2 Atualizar as views

from django.contrib.auth.mixins import LoginRequiredMixin, PermissionRequiredMixin
from django.urls import reverse_lazy
from django.views.generic import ListView, CreateView, UpdateView, DeleteView
from nome_do_seu_app.forms import PersonForm
from nome_do_seu_app.models import Person


class PersonListView(LoginRequiredMixin, ListView):
    ...


class PersonCreateView(LoginRequiredMixin, PermissionRequiredMixin, CreateView):
    permission_required = "nome_do_seu_app.add_person"
    ...


class PersonUpdateView(LoginRequiredMixin, PermissionRequiredMixin, UpdateView):
    permission_required = "nome_do_seu_app.change_person"
    ...


class PersonDeleteView(LoginRequiredMixin, PermissionRequiredMixin, DeleteView):
    permission_required = "nome_do_seu_app.delete_person"
    ...
Ordem das classes
Os mixins vêm antes da view genérica (CreateView, UpdateView...). Senão a página abre antes da verificação.
permission_required
A permissão exigida, no formato app.acao_model. O Django cria quatro para cada model, sozinho, no migrate: add_person, change_person, delete_person e view_person.
Os dois juntos
O LoginRequiredMixin vem primeiro: quem não está logado vai para o login. Depois o PermissionRequiredMixin confere a permissão de quem já entrou.

3 Dar permissão a um usuário

No admin (/admin), abra Usuários, escolha o usuário e, em Permissões do usuário, adicione por exemplo Can add person. Para vários usuários de uma vez, crie um Grupo com as permissões e coloque os usuários nele.

4 Esconder os botões de quem não pode

Opcional, mas evita botão que leva a um 403. O template recebe as permissões em {{ perms }}:

{% for person in people %}
    <li>
        {{ person.first_name }} {{ person.last_name }}
        {% if perms.nome_do_seu_app.change_person %}
            <a href="{% url 'nome_do_seu_app:person_update' person.pk %}" class="btn btn-sm btn-primary">Editar</a>
        {% endif %}
        {% if perms.nome_do_seu_app.delete_person %}
            <a href="{% url 'nome_do_seu_app:person_delete' person.pk %}" class="btn btn-sm btn-danger">Excluir</a>
        {% endif %}
    </li>
{% endfor %}

✓ Resultado esperado

Sem login, /pessoas/ manda para a tela de login. Logado com uma conta nova, a lista aparece, mas sem os botões Editar e Excluir, e abrir /pessoas/nova/ dá 403. Com o superusuário, tudo funciona.

Superusuário

O superusuário tem todas as permissões automaticamente, não precisa marcar nenhuma.

Esconder o botão não basta

O {% if perms %} só esconde o botão. Quem digitar a URL direto ainda chega na view, e é o PermissionRequiredMixin que bloqueia. Use os dois.
